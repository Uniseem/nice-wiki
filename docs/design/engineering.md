# 工程规范：测试、过程记录、AI 助手说明文件（草案）

> 状态：讨论中。对应决策记录 D36–D40。标 🟡 的是建议做法，可以推翻。

## 目标

项目会持续变大，而且大部分代码会由 AI 编程助手（Claude Code 等）编写。要保证三件事：

1. 任何一次会话开始时，助手都能用最少的阅读量知道：项目是什么、现在进行到哪、这次该做什么、有哪些规矩。
2. 每一块代码在写完的当下就有测试，后面的改动不会悄悄把它弄坏。
3. 文档描述的始终是现在的真实情况，而不是三个月前的计划。

## 一、文档按"生命周期"分类

文档容易过时，最主要的原因是把不同性质的内容混在一起写。所以按"多久变一次、怎么变"来分类：

| 文档 | 回答的问题 | 怎么变 | 位置 |
|---|---|---|---|
| 设计文档 | 系统是什么样、为什么 | 设计变了就改，和代码同一次提交 | `docs/design/*.md` |
| 决策记录 | 当初为什么这样选 | 只追加；推翻旧决策时写一条新的，旧的标为"已被取代" | `docs/adr/`，一条一个文件 |
| 实施计划 | 要做哪些任务、每个任务怎么算完成 | 范围变化时修改；任务完成时打勾 | `docs/plan.md` |
| 状态快照 | 现在进行到哪了 | **随时覆盖**，只保留当前情况 | `STATUS.md`（根目录） |
| 过程记录 | 每次 push 包含了什么、过程中遇到什么问题 | **只追加**，不修改 | `docs/push-log/` |
| 操作手册 | 某类重复操作具体怎么做 | 流程变了就改 | `docs/playbooks/*.md` |
| 更新日志 | 每个版本对使用者来说有什么变化 | 发布版本时追加 | `CHANGELOG.md` |

### 状态快照 `STATUS.md`

每次会话开始时都要读，所以必须短，控制在一屏以内。内容固定为五节：

```markdown
# 当前状态（更新于 2026-10-20）

## 当前阶段
阶段 2：后台与编辑器（进度 6/14）

## 进行中
- P2-07 超级块：拖拽进栏已完成，栏宽调节未做

## 下一步
- P2-08 画板（Excalidraw）

## 阻塞与待决
- 抖音嵌入播放器的地址格式未验证（影响 P2-11）

## 已知问题与技术债
- 编辑锁的心跳间隔是写死的，应改为配置项
```

### 过程记录 `docs/push-log/` ✅

**以 push 为单位记录。push 严格由用户手动触发**，AI 助手绝不主动 push。

```
docs/push-log/
├── INDEX.md                 # 索引：每次 push 的编号、日期、涉及任务、一句话摘要
├── _pending.md              # 上次 push 之后各次会话的记录，push 时整理并清空
├── 2026-10-20-0001.md
├── 2026-10-22-0002.md
└── ...
```

- 文件名是"push 当天的日期-序号"。序号全局递增，不按天重新计数，所以单看序号就知道先后。
- **两次 push 之间**：每次会话结束时，助手往 `_pending.md` 追加一段：

  ```markdown
  ## 2026-10-20 · P2-07 超级块
  - 做了什么：拖拽块进入某一栏；空栏的占位提示
  - 临时决定：栏数上限放在 schema 里校验，而不是只在界面上限制
  - 遇到的问题：DragHandle 在嵌套节点里定位不准，改用 ……
  - 留给下次：栏宽调节；窄屏改为上下排列的断点
  ```

- **你说"push"时**，按 `docs/playbooks/push.md` 的步骤执行：
  1. `make check` 必须全部通过，否则停下来报告；
  2. **扫描所有待推送的提交**，包括提交信息、文件内容、作者信息，确认没有隐私信息（见 D42）。发现问题就停下来报告；
  3. 汇总上次 push 之后的所有提交，以及 `_pending.md` 里的会话记录；
  4. 写成正式的记录文件（格式见下），并清空 `_pending.md`；
  5. 在 `INDEX.md` 里追加一行；
  6. 提交这些记录文件；
  7. 执行 `git push`。

  每次 push 都要你明确说了才执行；上一次的同意不代表下一次也同意。

- **正式记录的格式**：

  ```markdown
  # Push 0007 · 2026-10-20

  - 提交范围：上次 push（e4f5a6b）之后的 12 个提交
  - 涉及任务：P2-06、P2-07（完成），P2-08（进行中）
  - 参与的模型：Claude Opus 5.5（10 个提交）、……（2 个提交）

  ## 完成了什么
  ## 过程中的小决定（没有写成决策记录的）
  ## 遇到的问题与解决办法
  ## 新增的技术债和遗留问题
  ## 下一步
  ```

- **索引另外维护**：`INDEX.md` 是按 push 排列的总表。另外，`docs/plan.md` 里每个任务完成时，注明是在哪次 push 里完成的，例如"✅ 完成于 push 0007"，这样从任务也能反查到过程记录。

git 提交信息和过程记录的分工：提交信息写"改了什么"；过程记录写"为什么这样做、试过什么、还剩什么"，也就是代码里看不出来的东西。

### 实施计划 `docs/plan.md`

- 按阶段划分，每个任务有编号（例如 `P2-07`），提交信息、过程记录、`STATUS.md` 里都用这个编号互相引用。
- 每个任务写明：
  - 要做什么
  - 依赖哪些任务
  - **验收标准**：做到什么程度算完成
  - **建议的测试**：建议写哪些测试。只是建议，**要用户同意后才写**（见第三部分）
- 任务的粒度：一个任务应该能在一到两次会话内完成。太大的任务要先拆开。

## 二、AI 助手说明文件

### 文件布局

```
nice-wiki/
├── AGENTS.md            # 所有 AI 助手共用的总说明
├── CLAUDE.md            # 只有一行：@AGENTS.md
├── server/AGENTS.md     # Go 端的约定
├── server/CLAUDE.md     # 只有一行：@AGENTS.md
├── web/AGENTS.md        # 前端的约定
└── web/CLAUDE.md        # 只有一行：@AGENTS.md
```

- **`AGENTS.md` 是唯一真实的内容。** 它是 Codex、Cursor、Copilot 等多数工具都认的通用约定。Claude Code 读取的是 `CLAUDE.md`，所以 `CLAUDE.md` 里只写一行 `@AGENTS.md`，把内容引用进来。这样换用哪个工具，读到的都是同一份说明。
- **分层存放。** 根目录的说明每次会话都会读；`server/`、`web/` 下的说明只在助手处理那部分代码时才读。各层只写自己范围内的事，不重复。
- **将来某个包变复杂了**（例如渲染器 `server/internal/doc/`），可以在那个目录下再加一份。

### 写什么、不写什么

这些文件每次都会占用助手的上下文，所以只写**看代码看不出来、但做错了代价很大**的东西。详细内容放在 `docs/` 里，说明文件里只放链接。

**根目录 `AGENTS.md` 的提纲：**

1. 一段话说明项目是什么，并附上文档索引（链接到 `docs/design/`、`docs/plan.md`、`STATUS.md`）
2. 目录地图：每个顶层目录是做什么的
3. 常用命令：`make dev`、`make test`、`make check` 等
4. **会话流程**：
   - 开始时：读 `STATUS.md` → 找到 `docs/plan.md` 里对应的任务 → 读相关的设计文档
   - 结束时：`make check` 全部通过 → 在 `plan.md` 里打勾 → 更新 `STATUS.md` → 往 `docs/push-log/_pending.md` 追加记录 → 提交
   - **绝不主动 push**，只有用户明确要求时才按 `docs/playbooks/push.md` 执行
5. **完成的定义**：代码和相关文档都更新了，并且 `make check` 全部通过，才能说"完成"。测试只在用户同意后才写，不算在完成的定义里
6. **测试规则（硬性规定）**：
   - 可以自行运行已有的检查：格式化、lint、类型检查、已有的测试
   - **以下操作必须先问用户，得到同意后才能做**：
     - 新增或修改任何测试，包括样例文档和快照
     - 在计划里增加测试阶段、测试任务
     - 运行花钱或耗时的测试：端到端测试、真实接口测试（`LIVE=1`）、AI 评测（`make eval`）
   - **已有测试失败时，只能修改业务代码，或者停下来报告。** 不能为了让测试通过而修改、删除、跳过测试
7. **提交署名（硬性规定）**：
   - 提交的作者是用户本人的 git 身份，不修改 git 配置
   - 每个提交末尾都用 `Co-Authored-By` 写明**本次会话实际使用的模型**，名称和版本要准确，从自己的运行环境信息里获取
   - 不确定自己是哪个模型时，先问用户，不能猜
   - 一个提交由多个模型参与时，每个模型各写一行
   - **提交中不得包含隐私信息**：真实邮箱、本机路径和用户名、真实 IP、密钥、访客数据等。作者邮箱只能是 GitHub 代用地址。每次提交前、push 前都要检查（见 D42）
8. **不变量**，也就是绝对不能破坏的规则，例如：
   - 块 ID 一旦生成就不能改
   - 文档 JSON 的结构有变化时，必须提升 `schemaVersion` 并编写迁移
   - 新增块类型时，按 `docs/playbooks/add-block.md` 把所有涉及的地方一次改全
   - 密钥、账号文件不能进 git；日志里不能记录访客提问的内容
   - 后台接口必须声明它需要的权限（见下文的权限测试）
   - 改接口先改 `api/openapi.yaml`，再运行代码生成，不手改生成的代码
   - 不主动 push
9. 提交规范（见第四部分）

**`server/AGENTS.md` 的提纲：**
- 包的划分，以及包之间允许的依赖方向
- 修改数据库：先写迁移文件，再写 `queries/*.sql`，然后运行 `make sqlc`，不要手改生成的代码
- 错误处理、日志（`log/slog`）、配置读取的写法
- 测试的写法和命令（见第三部分）

**`web/AGENTS.md` 的提纲：**
- 两个入口（`admin`、`site`）分别放在哪，`shared/` 里放什么
- 组件统一用 `<script setup lang="ts">`；shadcn-vue 组件放在哪个目录、怎么添加新组件
- 样式只用 Tailwind 和设计变量，不写死颜色
- 调用接口统一走生成的 API 客户端，不直接写 `fetch`
- 测试的写法和命令

### 操作手册 `docs/playbooks/`

有些操作每次都要改很多地方，漏改一处就会出问题，把它们写成手册：

| 手册 | 内容 |
|---|---|
| `add-block.md` | 新增一种块：编辑器扩展、Go 的三个渲染器（HTML、纯文本、Markdown）、共用样式、AI 检索单元、翻译时要提取的文本；最后询问用户是否添加样例文档和快照 |
| `add-api.md` | 新增一个接口：在 API 定义里声明、生成代码、声明需要的权限、写测试 |
| `add-migration.md` | 新增数据库迁移，或者文档格式迁移 |
| `add-language.md` | 在内置语言清单里新增一种语言 |
| `add-video-provider.md` | 新增一个视频平台 |
| `push.md` | 用户要求 push 时的完整步骤：检查、写过程记录、更新索引、提交、push |

以后如果发现某本手册用得很频繁，可以再把它包装成 Claude Code 的 skill。手册本身保持和工具无关。

## 三、测试规范

### 谁来决定写什么测试 ✅

**测试由用户决定，AI 助手不能自行增加。** 这条写进 `AGENTS.md` 的硬性规定：

| 操作 | AI 助手能否自行进行 |
|---|---|
| 运行格式化、lint、类型检查 | 可以 |
| 运行已有的测试 | 可以 |
| 新增或修改测试（包括样例文档、快照） | **必须先问** |
| 在计划里增加测试阶段或测试任务 | **必须先问** |
| 运行端到端测试、真实接口测试、AI 评测 | **必须先问**（花钱或耗时） |
| 已有测试失败时修改、删除、跳过这个测试 | **不允许**，只能改业务代码，或者停下来报告 |

AI 助手觉得某处值得测试时，可以提出建议，说明测什么、为什么，由用户决定写不写。

下面的内容是**用户同意写测试之后**应该遵守的写法。

### 写法上的原则

- **不设覆盖率指标。** 用户决定要测的地方，优先考虑以下几类：
  - 修过的 bug：写一个能复现它的测试，防止再次出现；
  - 块类型：每种块都有样例文档；
  - 后台接口：权限测试。
- **普通测试里绝不调用真实的模型接口。** 原因：花钱、慢、结果不稳定。

### 分层

| 层 | 测什么 | 工具 | 什么时候跑 |
|---|---|---|---|
| Go 单元测试 | 单个函数、单个包 | 标准库 `testing` + `go-cmp` 🟡 | 每次 `make test` |
| 样例快照测试 | 三个渲染器的输出、拆块结果、检索单元组装 | 样例文档 + 期望输出文件 | 每次 `make test` |
| Go 集成测试 | HTTP 接口、权限、发布流程、git 记录 | `httptest` + 临时目录里的真实 SQLite 和 `data/` | 每次 `make test` |
| 前端单元测试 | 工具函数、组合式函数、Tiptap 扩展 | Vitest | 每次 `make test` |
| 前后端一致性测试 | Tiptap 的 `generateHTML` 和 Go 渲染出的 HTML 结构一致 | Vitest 生成标准输出，Go 测试比对 | 每次 `make test` |
| 端到端测试 | 关键流程走一遍：注册 → 建文档 → 发布 → 公开页面能看到 | Playwright | 每个阶段结束时，以及发版前 |
| AI 质量评测 | 检索准不准、回答好不好 | 评测题集 + 真实模型 | 手动运行（花钱） |

### 样例文档：前后端共用

```
fixtures/
├── docs/                     # 样例文档（Tiptap JSON），每种块至少一个
│   ├── paragraph-marks.json
│   ├── columns-nested.json
│   └── ...
└── expected/                 # 期望输出，由测试生成，提交进 git
    ├── paragraph-marks.html
    ├── paragraph-marks.txt
    ├── paragraph-marks.md
    └── ...
```

- Go 测试读取 `fixtures/docs/`，把三个渲染器的输出和 `expected/` 比对。渲染器的改动是有意为之时，运行 `make test-update` 重新生成期望输出，再在 diff 里逐一确认变化。
- 一致性测试：先由 Vitest 用 Tiptap 的 `generateHTML` 生成标准 HTML，再和 Go 的输出比对。比对前做规范化：忽略属性顺序和空白，忽略 Go 端额外加的属性（如 `srcset`、`loading`）。
- 新增块类型时，`add-block.md` 的最后一步是询问用户是否添加样例文档和快照。

### 外部服务：用假实现代替

- 模型渠道、Turnstile、GeoIP、视频平台，都通过 Go 接口调用。测试时换成假实现，返回事先写好的结果。
- 每个外部服务另外保留少量"真实调用"测试，默认不运行。设置环境变量（例如 `LIVE=1`）时才运行，用来确认对方的接口没有变。

### 和时间有关的逻辑

编辑锁超时、IP 封禁 10 分钟、缓存有效期、每日花费上限，这类逻辑都依赖时间。用 Go 1.25 起正式提供的 `testing/synctest` 测试，时间可以瞬间"快进"，不需要真的等，结果也稳定。

### 权限测试

- 每个后台接口在注册路由时都必须声明它需要的权限。
- 有一个测试会遍历所有路由：没有声明权限的路由直接判为失败；声明了的，逐个用"有权限"和"没有权限"的账号各请求一次，确认结果符合预期。
- 这样以后新增接口时，不可能忘了加权限检查。

### AI 质量评测

```
evals/
├── qa.yaml              # 评测题：问题、应该命中的文档或块、要点
└── results/             # 每次评测的结果，按日期保存
```

- 衡量指标：
  - 检索：正确的块是否出现在前 K 个结果里（召回率）、排在第几位
  - 回答：由模型对照要点打分
- `make eval` 用真实模型跑一遍，会花钱，所以只手动运行。
- 更换模型、调整检索参数之后跑一次，把结果和上一次对比，才能知道这次改动是变好了还是变坏了。

## 四、代码风格与提交规范

### 自动检查

`make check` 一条命令跑完所有检查，全部通过才算完成。它只运行已有的检查，AI 助手可以自行运行：

| 范围 | 检查项 |
|---|---|
| Go | `gofmt`、`go vet`、`golangci-lint`、`go test -race ./...` |
| 前端 | ESLint、`vue-tsc` 类型检查、Vitest |
| 生成的代码 | 重新运行 sqlc 和 API 代码生成，确认和仓库里的一致（防止有人手改生成的代码） |
| 隐私 | 扫描改动里的邮箱、本机路径、IP、密钥等（D42）。同时接入 git 提交钩子 |

可以加一个 git 提交前的钩子，自动运行其中速度快的部分（格式化、lint）。

### 语言 ✅

代码注释、提交信息、`AGENTS.md`、所有文档都用中文；变量名、函数名等标识符用英文。

### 提交信息 ✅

使用 Conventional Commits 格式，类型前缀用英文，描述用中文，带上范围和任务编号：

```
feat(server): 文档发布时写入 git 记录 [P2-03]
fix(web): 超级块在窄屏下不换行 [P2-07]
docs: 更新 STATUS.md
```

一个任务可以分多次提交，但每次提交都要保证 `make check` 能通过。

### 提交署名 ✅

**提交的作者是用户本人，AI 模型作为合著者，写在提交信息的末尾：**

```
feat(server): 文档发布时写入 git 记录 [P2-03]

发布时把正文和译文的变化提交到 data/ 的 git 仓库，作者为执行发布的后台账号。

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

- 作者：本机 git 配置的身份，也就是用户的 GitHub 账号（目前是 Uniseem 的 noreply 邮箱）。AI 助手不能修改 git 配置。
- 合著者：本次会话**实际使用的模型**，名称和版本都要准确。邮箱必须是这个 AI 在 GitHub 上对应账号的邮箱，这样才会计入仓库的贡献统计。
- 不确定自己是哪个模型时，先问用户，不能猜。
- 一个提交由多个模型参与时，每个模型各写一行。

各 AI 的署名身份：

| AI | 署名格式 |
|---|---|
| Claude（Anthropic） | `Co-Authored-By: Claude <模型名和版本> <noreply@anthropic.com>` |
| 其他工具 | 第一次使用时询问用户，确认对应 GitHub 账号的邮箱后补进这张表 |

**第一次 push 之后要确认一次**：GitHub 仓库的贡献者列表里确实出现了 AI 的账号。如果没有，改成"AI 作为提交作者、用户作为提交者"的方式（见 D41）。

## 五、前后端接口约定 ✅

前后端之间的接口是最容易出现"两边对不上"的地方。建议以 **OpenAPI 定义文件为唯一依据**：

- 接口写在 `api/openapi.yaml` 里。
- 用 oapi-codegen 生成 Go 端的请求和响应类型，以及路由接口；它支持生成标准库 `net/http` 的代码。
- 用 openapi-typescript 生成前端的类型和请求客户端。
- 修改接口的流程：先改 `openapi.yaml`，再运行代码生成，然后两边按编译错误修改。

这样接口一改，两边的编译器或类型检查都会报错，不会等到运行时才发现对不上。
