# 多语言设计（草案）

> 状态：讨论中。对应决策记录 D11–D13。

## 目标

- 站点初始化时指定一种基准语言（默认中文）。你只用基准语言写作。
- 后台可以勾选多种目标语言，由大模型把全站翻译过去，之后增量同步。
- 访客按浏览器语言自动进入对应版本；系统判断访客可能更适合另一种语言时，弹窗询问是否切换。

## 翻译以块为单位

块级设计在这里正好派上用场：

- **译文沿用原文的块 ID。** 不同语言的同一篇文档，块树结构完全一样，只是文字不同。所以锚点链接、AI 回答里的块引用、语言切换后停在同一位置，在所有语言下都能直接用。
- **增量翻译。** 每个块的译文记录它翻译时原文的内容哈希。原文改了，只重新翻译哈希变化的块。

### 翻译流程（发布文档时触发，后台异步执行）

1. 找出这篇文档里需要翻译的块：新增的块，以及原文哈希变了的块。
2. 一次请求发送：整篇原文（作为上下文，配合提示缓存）、需要翻译的块、术语表。
3. 模型按块 ID 返回译文（结构化 JSON）。
4. 校验：块 ID 一个不少，行内标记结构完整。
5. 写入译文文件。

### 行内格式的保护

块内的加粗、链接、行内代码等，转换成带编号的占位标签交给模型：

```
点击 <b1>设置</b1>，然后查看<a1>帮助文档</a1>中的 <c1/>
```

- 链接地址、行内代码不交给模型，只保留占位符，翻译完再还原，避免模型改坏 URL 和代码。
- 代码块、公式、嵌入内容不翻译。
- 图片的替代文字和图注要翻译。

### 术语表

后台维护一张表：哪些词不翻译（产品名、品牌名），哪些词在某种语言里有固定译法。每次翻译都带上它，保证全站用词一致。

### 人工修改译文 🟡

允许在后台手动修改某个块的译文，修改后标记为"人工"。

- 机器译文：原文变化后自动重新翻译。
- 人工译文：原文变化后不会被覆盖，而是标记为"待复核"，在后台提示你处理。

### 翻译过程中访问会怎样

新译文生成之前，继续显示旧译文。新增的块还没有译文时，先显示原文。

### 还要翻译什么

| 内容 | 怎么处理 |
|---|---|
| 文档标题、目录树 | 和正文一起翻译 |
| 站点名称、导航等站点设置 | 走同一套翻译流程 |
| 前端界面文字（按钮、提示等） | 基准语言的界面文字由开发者维护；新增目标语言时，用同一套流程翻译 |
| 图片里的文字、附件内容 | 不翻译 |

### 成本估算

几百篇文章，按每篇 3000 字计算，基准语言约 100 万 token。每种语言的初次全站翻译：
- 中档模型：约几美元
- 顶级模型：约 20 美元

之后的增量翻译成本可以忽略。

## 存储

译文是"人可能会修改的内容"，和正文一样以文件为真实数据：

```
data/
├── docs/                       # 基准语言正文
└── i18n/
    └── <lang>/<doc-id>.json    # 某篇文档在某种语言下的译文
```

译文文件按块 ID 组织，每个块记录：译文内容、翻译时的原文哈希、来源（机器 / 人工）、状态（正常 / 待复核）。

由此形成一条原则：**正文、译文这类内容都存成文件；数据库只存索引，以及模型生成的检索数据。**

## URL 结构 🟡

所有语言都带前缀，包括基准语言：

```
/                    → 根据访客语言跳转（见下文）
/zh/<页面路径>
/en/<页面路径>
```

SEO 方面：
- 每个页面输出 `hreflang` 标签，列出这个页面的所有语言版本，另加一个 `x-default` 指向 `/`。
- `<html lang>` 写当前语言。
- 每种语言单独生成 sitemap。

## 语言判断与切换

### 第一层：服务端跳转（即时）

只对根路径 `/` 生效，按顺序判断：

1. cookie 里有用户明确选过的语言 → 用它。
2. 用浏览器的 `Accept-Language` 匹配已启用的语言。要处理地区变体：`zh-TW`、`zh-HK` 匹配繁体，`zh-CN`、`zh-SG` 匹配简体，`pt-BR` 匹配葡萄牙语。
3. 都匹配不上 → 基准语言。

返回 302 跳转，响应头带 `Vary: Accept-Language`。

**带语言前缀的页面一律不强制跳转。** 原因有两个：
- 搜索引擎爬虫一般不带语言偏好，强制跳转会让其他语言版本无法被收录。
- 别人分享给你一个 `/zh/` 链接，你点开就应该看到中文。

### 第二层：切换建议（页面加载后异步执行）

触发条件：用户没有明确选过语言，也没有拒绝过建议。

1. 前端收集 `navigator.languages`（浏览器语言列表）和时区（例如 `Asia/Shanghai`），发给后端。
2. 后端补充 IP 归属国家：使用本地离线的 GeoIP 库（例如 DB-IP Lite），不调用第三方服务，也不保存 IP。
3. 交给快速模型判断，得出建议语言和置信度。
   - 结果按"浏览器语言 + 时区 + 国家"的组合缓存。
   - 模型超时或出错时退回规则判断。
4. 如果建议语言和当前页面语言不同、站点启用了这种语言、并且置信度够高，就弹出提示。
   - **提示文字用建议的那种语言写**，因为访客未必看得懂当前页面的语言。
5. 访客选择切换 → 记 cookie，跳转到同一篇文档的另一种语言版本。访客拒绝 → 记 cookie，不再询问。

说明：浏览器拿不到 DNS 信息，服务端能拿到的是访客 IP，所以位置信号用 IP 归属地。

### 判断依据（同时用作模型提示词和兜底规则）

- `navigator.languages` 是语言偏好最强的信号，排第一的语言权重最高。
- 时区和 IP 国家是辅助信号。典型场景：浏览器语言是 `en-US`（很多电脑出厂默认如此），但时区是 `Asia/Shanghai`、IP 在中国，这时建议中文。
- 位置只能作为参考：旅行、VPN、海外华人、多语言国家（瑞士、加拿大）都会让位置信号失真。所以只有多个信号一致时才弹窗。

## 对 AI 问答的影响

- **只给基准语言建索引。** 前置模型改写问题时，顺便把问题翻译成基准语言再检索。只维护一份索引，关键词召回也不会因为语言不同而失效。
- **聪明模型用访客的语言回答。** 交给它的材料优先用对应语言的译文（同一个块 ID 直接取），这样回答里的用词和访客在页面上看到的一致。
- 回答里的块引用链接到当前语言版本的页面。

## 前端布局

CSS 从第一天起就用逻辑方向属性（`margin-inline-start` 而不是 `margin-left`）。这几乎不增加成本，以后要支持阿拉伯语这类从右到左的语言时，不需要返工。是否开放这类语言，以后再决定。🟡

## 语言列表

语言列表本身几乎没有成本：一种语言只是一个语言代码加一个显示名，翻译交给模型。
系统内置一份常用语言清单，后台随时勾选启用。

初始清单（草案）：
